## ملخص تنفيذي

يعتمد نظام صلاحيات OpenProject على **أربعة مستويات تنظيمية** (Organizational Levels) يتم من خلالها تحديد ما يمكن للمستخدم رؤيته وفعله. هذه المستويات ليست "نطاقات" أو "سياقات" بل هي **طبقات تنظيمية** تتدرج من الأعلى (النظام بالكامل) إلى الأسفل (حزمة عمل فردية).

---

## المستويات التنظيمية الأربعة

### المستوى 1: مستوى النظام / المثيل (System / Instance Level)

| الخاصية | الوصف |
| --------- | ------- |
| **المسمى الرسمي** | Administrator |
| **النطاق** | المثيل بالكامل (Entire Instance) |
| **من يملكه** | مدير النظام (System Administrator) |
| **قابل للتخصيص** | ❌ لا - صلاحيات ثابتة غير قابلة للتعديل |
| **مكان الإدارة** | Administration → قائمة الإدارة عبر أيقونة المستخدم |

**الوصف:**
هذا هو أعلى مستوى في النظام. المستخدم الذي يحمل صفة Administrator يملك تحكمًا كاملاً وغير مقيد بكامل مثيل OpenProject، بما يشمل:

- إعدادات النظام (System Settings)
- إدارة المستخدمين (User Management)
- أرشفة المشاريع وحذفها
- تكوين الأدوار العامة وأدوار المشاريع
- إدارة المجموعات (Groups)
- إعدادات المصادقة والأمان
- إدارة الإضافات والتكاملات

**ملاحظة مهمة:** صلاحيات المدير ثابتة (fixed) ولا يمكن تعديلها أو تقليصها. هي حزمة "الكل أو لا شيء".

---

### المستوى 2: المستوى العام / عبر المشاريع (Global Level)

| الخاصية | الوصف |
| --------- | ------- |
| **المسمى الرسمي** | Global Roles |
| **النطاق** | عبر المثيل بالكامل لكن بصلاحيات محددة |
| **من يملكه** | مستخدمون يُعيّن لهم دور عام |
| **قابل للتخصيص** | ✅ نعم - يمكن إنشاء أدوار عامة مخصصة |
| **مكان الإدارة** | Administration → Users and Permissions → Roles and Permissions |

**الوصف:**
الأدوار العامة (Global Roles) تسمح لمدير النظام بتفويض مهام إدارية محددة لمستخدمين دون منحهم صلاحيات المدير الكاملة. هذه الأدوار تعمل على مستوى المثيل بأكمله ولكنها مقيدة بصلاحيات محددة.

**أمثلة على الصلاحيات العامة:**

- إنشاء مشاريع جديدة (Create projects)
- إدارة المستخدمين (Manage users)
- عرض قائمة المشاريع العامة
- إدارة الإضافات (Manage plugins)

**الفرق الجوهري عن مستوى النظام:**

- مدير النظام: كل شيء، بلا قيود
- الدور العام: صلاحيات إدارية **مُنتقاة** يحددها المدير

**كيفية التعيين:**
يتم تعيين الأدوار العامة من خلال صفحة إدارة المستخدمين. يمكن لمستخدم واحد أن يحمل دورًا عامًا واحدًا أو أكثر بالتوازي مع أدوار مشروع.

---

### المستوى 3: مستوى المشروع (Project Level)

| الخاصية | الوصف |
| --------- | ------- |
| **المسمى الرسمي** | Project Roles |
| **النطاق** | مشروع محدد واحد |
| **من يملكه** | أعضاء المشروع (Project Members) |
| **قابل للتخصيص** | ✅ نعم - يمكن إنشاء أدوار مشروع مخصصة |
| **مكان الإدارة** | Administration → Roles and Permissions (تعريف) ثم Project → Members (تعيين) |

**الوصف:**
هذا هو المستوى الأساسي والأكثر استخدامًا في نظام الصلاحيات. أدوار المشروع تحدد ما يمكن لكل عضو رؤيته والقيام به داخل مشروع بعينه.

#### أنواع أدوار المشروع

##### أ. الأدوار المخصصة (Custom Project Roles)

أدوار يُنشئها المدير حسب الحاجة، مثل:

- **Member** (العضو) - الدور الافتراضي
- **Project Admin** (مدير المشروع) - صلاحيات إدارية داخل المشروع
- **Reader** (القارئ) - عرض فقط
- أدوار مخصصة أخرى حسب متطلبات المنظمة

##### ب. الأدوار المدمجة الخاصة (Built-in Special Roles)

| الدور | الوصف | الشرط |
|-------|-------|-------|
| **Non-member** | ينطبق على المستخدمين المسجلين الذين ليسوا أعضاء في المشروع | المشروع يجب أن يكون **عام** (Public) |
| **Anonymous** | ينطبق على الزوار غير المسجلين | المشروع عام + تعطيل إلزام المصادقة |

**علاقة الصلاحيات بالوحدات (Modules):**
هذه نقطة حاسمة - حتى لو كان لدى المستخدم صلاحية معينة في دوره، فإن هذه الصلاحية **لن تعمل** إلا إذا كانت الوحدة المقابلة مُفعّلة في إعدادات المشروع. مثال:

- صلاحية "تعديل حزم العمل" → تتطلب تفعيل وحدة **Work Packages**
- صلاحية "تعديل الويكي" → تتطلب تفعيل وحدة **Wiki**
- صلاحية "إدارة الاجتماعات" → تتطلب تفعيل وحدة **Meetings**

**الوحدات المتاحة في المشروع:**

- Work Packages (حزم العمل)
- Gantt Charts (مخططات جانت)
- Agile Boards (اللوحات المرنة)
- Backlogs (القوائم المتأخرة)
- Calendar (التقويم)
- News (الأخبار)
- Forums (المنتديات)
- Wiki (الويكي)
- Repository (المستودع)
- Time Tracking (تتبع الوقت)
- Costs (التكاليف)
- Meetings (الاجتماعات)
- Budgets (الميزانيات)
- Team Planner (مخطط الفريق)

**آلية تعيين الأعضاء:**

- يتم من خلال: Project Menu → Members
- يمكن تعيين **مستخدمين أفراد** أو **مجموعات** (Groups)
- يمكن لمستخدم واحد أن يحمل أدوارًا مختلفة في مشاريع مختلفة
- يمكن تعيين أكثر من دور لنفس المستخدم في نفس المشروع

### المستوى 4: مستوى حزمة العمل (Work Package Level)

| الخاصية | الوصف |
| --------- | ------- |
| **المسمى الرسمي** | Work Package Sharing |
| **النطاق** | حزمة عمل فردية محددة |
| **من يملكه** | المستخدمون المُشارَك معهم |
| **قابل للتخصيص** | ✅ نعم - ثلاث مستويات وصول |
| **مكان الإدارة** | Work Package → زر Share |
| **متاح في** | ⚡ Enterprise Edition فقط |

**الوصف:**
هذا هو أدق مستوى للتحكم في الصلاحيات. يسمح بمشاركة حزمة عمل فردية مع مستخدمين ليسوا بالضرورة أعضاء في المشروع. هذه الميزة متاحة فقط في النسخة المؤسسية (Enterprise).

**مستويات الوصول عند المشاركة:**

| مستوى الوصول | الوصف |
| ------------- | ------- |
| **View** (عرض) | يمكن رؤية حزمة العمل فقط |
| **Comment** (تعليق) | يمكن رؤية حزمة العمل وإضافة تعليقات |
| **Edit** (تعديل) | يمكن رؤية وتعديل حزمة العمل |

**ملاحظات مهمة:**

- المشاركة لا تجعل المستخدم عضوًا في المشروع
- إذا تمت المشاركة مع شخص غير مسجل، سيُطلب منه التسجيل أولاً
- تتطلب عادةً صلاحية "Create users" العامة لاستخدام هذه الميزة
- لا يوجد نوع دور منفصل اسمه "work_package_role" - بل هو نظام مشاركة (sharing) يعمل بمستويات وصول

## جدول المقارنة الشامل

| المعيار | النظام (System) | العام (Global) | المشروع (Project) | حزمة العمل (Work Package) |
| --------- | ---------------- | ---------------- | ------------------- | -------------------------- |
| **نوع الدور** | Administrator | Global Role | Project Role | Sharing Level |
| **النطاق** | المثيل بالكامل | المثيل بالكامل | مشروع واحد | حزمة عمل واحدة |
| **قابل للتخصيص** | ❌ | ✅ | ✅ | ✅ (3 مستويات) |
| **يتطلب عضوية مشروع** | ❌ | ❌ | ✅ | ❌ |
| **يتأثر بالوحدات** | ❌ | ❌ | ✅ | ✅ |
| **عدد الأدوار** | 1 (ثابت) | متعدد (مخصص) | متعدد (مخصص + مدمج) | 3 (View/Comment/Edit) |
| **من يديره** | مدير النظام | مدير النظام | مدير المشروع | عضو المشروع المُخوّل |
| **الإصدار** | Community + Enterprise | Community + Enterprise | Community + Enterprise | Enterprise فقط |
| **التعيين عبر مجموعات** | ❌ (فردي) | ✅ | ✅ | ✅ |

## آلية تقييم الصلاحيات (Permission Evaluation Flow)

عند محاولة مستخدم تنفيذ إجراء معين، يتم تقييم الصلاحية وفق التسلسل التالي:

```
المستخدم يطلب إجراءً
        │
        ▼
┌───────────────────┐
│ هل هو Administrator? │──── نعم ──→ ✅ السماح (دائمًا)
└───────────────────┘
        │ لا
        ▼
┌───────────────────────┐
│ هل لديه دور عام يشمل  │──── نعم ──→ ✅ السماح
│ هذا الإجراء؟           │           (للإجراءات العامة فقط)
└───────────────────────┘
        │ لا
        ▼
┌────────────────────────┐
│ هل هو عضو في المشروع؟  │──── لا ──→ فحص Non-member/Anonymous
└────────────────────────┘
        │ نعم
        ▼
┌─────────────────────────┐
│ هل دوره يتضمن الصلاحية؟ │──── لا ──→ ❌ الرفض
└─────────────────────────┘
        │ نعم
        ▼
┌──────────────────────────┐
│ هل الوحدة المطلوبة       │──── لا ──→ ❌ الرفض
│ مُفعّلة في المشروع؟      │          (الصلاحية معطلة ضمنيًا)
└──────────────────────────┘
        │ نعم
        ▼
     ✅ السماح
```

## تفصيل صلاحيات كل مستوى

### صلاحيات المستوى 1 (النظام) - Administrator

صلاحيات ثابتة تشمل كل شيء في النظام بدون استثناء:

- إدارة كاملة لجميع المشاريع
- إدارة كاملة لجميع المستخدمين والمجموعات
- تكوين إعدادات النظام
- إدارة الأدوار والصلاحيات
- إدارة التكاملات والإضافات
- إدارة المصادقة والأمان
- الوصول لجميع البيانات في جميع المشاريع

### صلاحيات المستوى 2 (العام) - Global Roles

أمثلة على الصلاحيات التي يمكن تعيينها:

- `create_project` - إنشاء مشاريع جديدة
- `manage_user` - إدارة حسابات المستخدمين
- `manage_placeholder_user` - إدارة المستخدمين المؤقتين

### صلاحيات المستوى 3 (المشروع) - Project Roles

تنقسم إلى فئات حسب الوحدات:

#### حزم العمل (Work Packages)

- عرض حزم العمل
- إنشاء حزم العمل
- تعديل حزم العمل
- حذف حزم العمل
- نقل حزم العمل
- إضافة تعليقات
- إدارة المرفقات
- تعيين الإصدارات
- إدارة العلاقات

#### الوقت والتكاليف

- تسجيل الوقت
- تعديل سجلات الوقت
- عرض تقارير التكاليف
- إدارة الميزانيات

#### الويكي

- عرض صفحات الويكي
- تعديل صفحات الويكي
- حذف صفحات الويكي
- إدارة قائمة الويكي

#### المستودع

- تصفح المستودع
- إدارة المستودع
- عرض سجل التغييرات

#### الاجتماعات

- إنشاء اجتماعات
- تعديل الاجتماعات
- إغلاق/فتح بنود الاجتماع

#### المنتديات

- إدارة المنتديات
- إنشاء مواضيع
- الرد على المواضيع

#### الأخبار

- إدارة الأخبار
- إضافة تعليقات على الأخبار

#### إدارة المشروع

- تعديل إعدادات المشروع
- إدارة الأعضاء
- إدارة الإصدارات
- إنشاء مشاريع فرعية
- تفعيل/تعطيل الوحدات

## المجموعات (Groups) - آلية تنظيمية مساعدة

المجموعات ليست مستوى تنظيمي بحد ذاتها، بل هي **آلية تسهيل** لتعيين الصلاحيات:

| الخاصية | الوصف |
| --------- | ------- |
| **الغرض** | تجميع المستخدمين لتعيين الأدوار بشكل جماعي |
| **مكان الإنشاء** | Administration → Users and Permissions → Groups |
| **الاستخدام** | تعيين دور مشروع لمجموعة كاملة بدلاً من كل مستخدم على حدة |
| **الوراثة** | أعضاء المجموعة يرثون أدوار المجموعة تلقائيًا |

## ملاحظات معمارية مهمة

### 1. لا يوجد توريث هرمي بين المشاريع

على عكس بعض الأنظمة الأخرى، OpenProject **لا يدعم** توريث الصلاحيات من مشروع أب إلى مشروع فرعي. كل مشروع يُدار بشكل مستقل من حيث العضويات والأدوار.

### 2. تعدد الأدوار

يمكن لمستخدم واحد أن يحمل:

- أدوار عامة متعددة
- أدوار مشروع مختلفة في مشاريع مختلفة
- أكثر من دور في نفس المشروع (تُجمع الصلاحيات)

### 3. الصلاحيات تراكمية

عندما يحمل المستخدم أكثر من دور، الصلاحيات **تتراكم** (additive) - أي أن الصلاحية النهائية هي مجموع صلاحيات جميع الأدوار. لا يوجد مفهوم "الرفض الصريح" (explicit deny).

### 4. بنية الكود المصدري

OpenProject مبني على **Ruby on Rails**. فحص الصلاحيات يتم عبر:

- التحقق من أدوار المستخدم في السياق الحالي (مشروع أو عام)
- التحقق من أن الوحدة المطلوبة مُفعّلة
- مطابقة الصلاحية المطلوبة مع الصلاحيات المرتبطة بأدوار المستخدم

## الفرق بين المستويات التنظيمية والنطاقات/السياقات

| المفهوم | التعريف | مثال في OpenProject |
| --------- | --------- | --------------------- |
| **المستوى التنظيمي** (Organizational Level) | طبقة في التسلسل الهرمي تُحدد أين تُطبق الصلاحيات | System, Global, Project, Work Package |
| **النطاق** (Scope) | مدى تأثير دور أو صلاحية معينة | "هذا الدور يعمل على مستوى المشروع فقط" |
| **السياق** (Context) | الظرف أو البيئة التي يتم فيها فحص الصلاحية | "هل المستخدم يعمل داخل مشروع X أم في واجهة الإدارة؟" |

**المستوى التنظيمي** يصف البنية الثابتة للنظام، بينما **النطاق** و**السياق** يصفان كيف يتم تطبيق هذه البنية في وقت التشغيل.
