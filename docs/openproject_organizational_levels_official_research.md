## ملخص تنفيذي

يعتمد نظام صلاحيات OpenProject على **أربعة مستويات تنظيمية رئيسية** (Organizational Levels) يتم من خلالها تحديد ما يمكن للمستخدم رؤيته والقيام به. هذه المستويات تتدرج من الأعلى (النظام بالكامل) إلى الأسفل (حزمة عمل فردية). بالإضافة إلى هذه المستويات، توجد **آليات تنظيمية مساعدة** (Groups, Placeholder Users, Modules, Project Templates) تعمل كأدوات تسهيل وضبط لا تُشكل مستويات مستقلة بحد ذاتها لكنها تؤثر جوهرياً على سلوك الصلاحيات.

## الجزء الأول: المستويات التنظيمية الأربعة

### المستوى 1: مستوى النظام / المثيل (System / Instance Level)

> **المصدر:** [Users and Permissions](https://www.openproject.org/docs/system-admin-guide/users-permissions/) - قسم Administration

| الخاصية | القيمة |
| --------- | -------- |
| **المسمى الرسمي** | Administrator |
| **النطاق** | المثيل بالكامل (Entire Instance) |
| **من يملكه** | مدير النظام (System Administrator) |
| **قابل للتخصيص** | ❌ لا - صلاحيات ثابتة غير قابلة للتعديل |
| **مكان الإدارة** | Administration → Users and Permissions |
| **الإصدار** | Community + Enterprise |

**الوصف الرسمي:**

المستخدم الذي يحمل صفة **Administrator** يمتلك تحكمًا كاملاً وغير مقيد بكامل مثيل OpenProject. هذه الصفة تُمنح من خلال تفعيل خيار "Administrator" في إعدادات حساب المستخدم.

**الصلاحيات الثابتة تشمل:**

- إدارة كاملة لجميع إعدادات النظام (System Settings)
- إدارة المستخدمين والمجموعات والأدوار
- إنشاء وأرشفة وحذف جميع المشاريع
- تكوين المصادقة والأمان (Authentication & Security)
- إدارة الإضافات والتكاملات
- الوصول الكامل لجميع البيانات في جميع المشاريع
- تكوين أنواع حزم العمل (Work Package Types)
- إدارة الحقول المخصصة (Custom Fields)
- تكوين سير العمل (Workflows)

**ملاحظة رسمية مهمة:**

> صلاحيات المدير هي حزمة "الكل أو لا شيء" (all-or-nothing) — لا يمكن تقييدها أو تقليصها. المدير يتجاوز جميع عمليات فحص الصلاحيات في النظام.

### المستوى 2: المستوى العام / عبر المشاريع (Global Level)

> **المصدر:** [Roles and Permissions](https://www.openproject.org/docs/system-admin-guide/users-permissions/roles-permissions/) - قسم Global Roles

| الخاصية | القيمة |
| --------- | -------- |
| **المسمى الرسمي** | Global Roles |
| **النطاق** | عبر المثيل بالكامل لكن بصلاحيات إدارية محددة |
| **من يملكه** | مستخدمون يُعيّن لهم دور عام |
| **قابل للتخصيص** | ✅ نعم - يمكن إنشاء أدوار عامة مخصصة |
| **مكان الإدارة** | Administration → Users and Permissions → Roles and Permissions |
| **الإصدار** | Community + Enterprise |

**الوصف الرسمي:**

الأدوار العامة (Global Roles) هي أدوار تُطبق على مستوى التطبيق بأكمله (application-level). تسمح لمدير النظام بتفويض مهام إدارية محددة لمستخدمين **دون منحهم صلاحيات المدير الكاملة**.

**كيفية إنشاء دور عام:**

1. الانتقال إلى: Administration → Users and Permissions → Roles and Permissions
2. الضغط على "**+ Role**" (زر إنشاء دور جديد)
3. تحديد نوع الدور كـ **"Global role"** (بدلاً من Project role)
4. تحديد الصلاحيات العامة المطلوبة
5. حفظ الدور

**أمثلة على الصلاحيات العامة المتاحة (من الوثائق الرسمية):**

| الصلاحية | الوصف |
| ---------- | ------- |
| `Create project` | إنشاء مشاريع جديدة |
| `Create project in project` | إنشاء مشاريع فرعية |
| `Manage user` | إدارة حسابات المستخدمين |
| `Create user` | إنشاء حسابات مستخدمين جديدة |
| `Manage placeholder user` | إدارة المستخدمين المؤقتين |

**كيفية تعيين دور عام لمستخدم:**

1. الانتقال إلى: Administration → Users and Permissions → Users
2. اختيار المستخدم
3. في تبويب "**Global Roles**"، إضافة الدور العام المطلوب

**الفرق الجوهري عن مستوى النظام:**

| الجانب | مدير النظام (Administrator) | الدور العام (Global Role) |
| -------- | ---------------------------- | -------------------------- |
| **الصلاحيات** | كل شيء بلا قيود | صلاحيات إدارية مُنتقاة |
| **التخصيص** | غير قابل للتعديل | قابل للتخصيص |
| **التفعيل** | خانة اختيار "Admin" في الحساب | تعيين دور عام محدد |
| **العدد** | دور واحد ثابت | أدوار متعددة مخصصة |

### المستوى 3: مستوى المشروع (Project Level)

> **المصدر:** [Roles and Permissions](https://www.openproject.org/docs/system-admin-guide/users-permissions/roles-permissions/) - قسم Project Roles + [Manage Members](https://www.openproject.org/docs/user-guide/members/)

| الخاصية | القيمة |
| --------- | -------- |
| **المسمى الرسمي** | Project Roles |
| **النطاق** | مشروع محدد واحد |
| **من يملكه** | أعضاء المشروع (Project Members) |
| **قابل للتخصيص** | ✅ نعم - يمكن إنشاء أدوار مشروع مخصصة |
| **مكان الإدارة** | Administration → Roles and Permissions (تعريف) ثم Project → Members (تعيين) |
| **الإصدار** | Community + Enterprise |

**الوصف الرسمي:**

هذا هو المستوى الأساسي والأكثر استخدامًا. أدوار المشروع (Project Roles) تحدد ما يمكن لكل عضو رؤيته والقيام به **داخل مشروع بعينه**.

#### أ. الأدوار المخصصة (Custom Project Roles)

أدوار يُنشئها المدير حسب احتياجات المنظمة. يأتي OpenProject مع أدوار افتراضية تشمل:

| الدور الافتراضي | الوصف |
| ---------------- | ------- |
| **Member** | الدور الأساسي للعضو العادي |
| **Project admin** | صلاحيات إدارية داخل المشروع المحدد |
| **Reader** | عرض فقط دون تعديل |

**كيفية إنشاء دور مشروع:**

1. Administration → Users and Permissions → Roles and Permissions
2. الضغط على "**+ Role**"
3. اختيار نوع الدور كـ **"Project role"**
4. تحديد الصلاحيات من القائمة المصنفة حسب الوحدات
5. حفظ الدور

#### ب. الأدوار المدمجة الخاصة (Built-in Special Roles)

> **المصدر:** [Roles and Permissions](https://www.openproject.org/docs/system-admin-guide/users-permissions/roles-permissions/) - قسم Non-member & Anonymous

| الدور | الوصف | الشرط | قابل للتعديل |
|-------|-------|-------|-------------|
| **Non-member** | ينطبق على المستخدمين المسجلين الذين ليسوا أعضاء في المشروع | المشروع يجب أن يكون **عام** (Public) | ✅ يمكن تعديل صلاحياته |
| **Anonymous** | ينطبق على الزوار غير المسجلين | المشروع عام + تعطيل إلزام المصادقة | ✅ يمكن تعديل صلاحياته |

**ملاحظة رسمية:** هذان الدوران لا يمكن حذفهما ولا إعادة تسميتهما، لكن يمكن تعديل الصلاحيات المرتبطة بهما. وهما يضمنان تحكمًا متسقًا في الوصول حتى للمستخدمين خارج فريق المشروع الأساسي.

#### ج. تصنيف الصلاحيات حسب الوحدات (Module-based Permissions)

> **المصدر:** [Project Settings - Modules](https://www.openproject.org/docs/user-guide/projects/project-settings/modules/)

الصلاحيات في OpenProject مُصنفة ومرتبطة بالوحدات (Modules). هذا يعني:

- حتى لو كان لدى المستخدم صلاحية معينة في دوره، **لن تعمل** إلا إذا كانت الوحدة المقابلة مُفعّلة في إعدادات المشروع
- تعطيل وحدة يُعطل ضمنياً جميع الصلاحيات المرتبطة بها

**فئات الصلاحيات الرسمية (حسب الوحدات):**

| الوحدة (Module) | أمثلة على الصلاحيات |
| ----------------- | --------------------- |
| **Work Packages** | عرض، إنشاء، تعديل، حذف، نقل، إضافة تعليقات، إدارة مرفقات، تعيين إصدارات، إدارة علاقات |
| **Gantt Charts** | عرض مخططات جانت |
| **Agile Boards** | إدارة لوحات Agile |
| **Backlogs** | إدارة القوائم المتأخرة (Scrum) |
| **Calendar** | عرض التقويم |
| **News** | إدارة الأخبار، إضافة تعليقات |
| **Forums** | إدارة المنتديات، إنشاء مواضيع، الرد |
| **Wiki** | عرض، تعديل، حذف، إدارة قائمة الويكي |
| **Repository** | تصفح المستودع، إدارته، عرض سجل التغييرات |
| **Time Tracking** | تسجيل الوقت، تعديل سجلات الوقت الخاصة/للآخرين |
| **Costs** | عرض تقارير التكاليف |
| **Budgets** | إدارة الميزانيات |
| **Meetings** | إنشاء اجتماعات، تعديل، إغلاق/فتح بنود |
| **Team Planner** | إدارة مخطط الفريق |
| **Members** | إدارة الأعضاء |
| **Project settings** | تعديل إعدادات المشروع |

#### د. آلية تعيين الأعضاء

> **المصدر:** [Manage Members](https://www.openproject.org/docs/user-guide/members/) + [Invite Members](https://www.openproject.org/docs/getting-started/invite-members/)

- يتم من خلال: Project Menu → **Members**
- يمكن تعيين **مستخدمين أفراد** أو **مجموعات** (Groups)
- يمكن لمستخدم واحد أن يحمل أدوارًا مختلفة في مشاريع مختلفة
- يمكن تعيين **أكثر من دور** لنفس المستخدم في نفس المشروع
- عند تعيين أدوار متعددة، الصلاحيات **تتراكم** (additive) — أي الصلاحية النهائية = مجموع صلاحيات جميع الأدوار

### المستوى 4: مستوى حزمة العمل (Work Package Level)

> **المصدر:** [Share Work Packages](https://www.openproject.org/docs/user-guide/work-packages/share-work-packages/)

| الخاصية | القيمة |
| --------- | -------- |
| **المسمى الرسمي** | Work Package Sharing |
| **النطاق** | حزمة عمل فردية محددة |
| **من يملكه** | المستخدمون المُشارَك معهم |
| **قابل للتخصيص** | ✅ نعم - ثلاث مستويات وصول |
| **مكان الإدارة** | Work Package → زر **Share** |
| **الإصدار** | ⚡ Enterprise Edition فقط |

**الوصف الرسمي:**

ميزة مشاركة حزم العمل (Work Package Sharing) تسمح بمشاركة حزمة عمل فردية مع مستخدمين أو مجموعات **ليسوا بالضرورة أعضاء في المشروع**. هذا يحافظ على مبدأ "مصدر الحقيقة الواحد" (single source of truth) من خلال السماح بالتعاون المباشر على المهمة.

**مستويات الوصول عند المشاركة:**

| مستوى الوصول | العرض | التعليق | التعديل |
| ------------- | ------- | --------- | --------- |
| **View** (عرض) | ✅ | ❌ | ❌ |
| **Comment** (تعليق) | ✅ | ✅ | ❌ |
| **Edit** (تعديل) | ✅ | ✅ | ✅ |

**ملاحظات رسمية مهمة:**

1. المشاركة **لا تجعل** المستخدم عضوًا في المشروع
2. يمكن المشاركة مع مستخدمين مسجلين أو دعوة مستخدمين جدد عبر البريد الإلكتروني
3. إذا تمت المشاركة مع شخص غير مسجل، سيُطلب منه التسجيل أولاً
4. لا يوجد نوع دور منفصل — بل هو نظام مشاركة (sharing) يعمل بمستويات وصول محددة
5. يحتاج المستخدم المُشارِك إلى صلاحية **"Share work packages"** في دوره

## الجزء الثاني: الآليات التنظيمية المساعدة

هذه ليست "مستويات" بحد ذاتها، بل هي **آليات مساعدة** تؤثر على كيفية تطبيق الصلاحيات وتوزيعها.

### الآلية 1: المجموعات (Groups)

> **المصدر:** [Groups](https://www.openproject.org/docs/system-admin-guide/users-permissions/groups/)

| الخاصية | القيمة |
| --------- | -------- |
| **الغرض** | تجميع المستخدمين لتعيين الأدوار بشكل جماعي |
| **مكان الإنشاء** | Administration → Users and Permissions → Groups |
| **الإصدار** | Community + Enterprise |

**الوصف الرسمي:**

المجموعات هي آلية لتجميع المستخدمين وتسهيل إدارة الصلاحيات. بدلاً من تعيين دور لكل مستخدم على حدة في كل مشروع، يتم:

1. إنشاء مجموعة
2. إضافة المستخدمين إليها
3. تعيين المجموعة كعضو في المشروع مع دور محدد
4. جميع أعضاء المجموعة **يرثون** تلقائيًا دور المجموعة في ذلك المشروع

**هرمية المجموعات (Group Hierarchy):**

> **اكتشاف مهم من المصادر الرسمية:**

OpenProject يدعم تنظيم المجموعات في هرمية من خلال تعيين **مجموعة أب (Parent Group)** لمجموعة فرعية:

| الخاصية | الوصف |
| --------- | ------- |
| **آلية التعيين** | تعيين parent group لمجموعة فرعية عند إنشائها أو تعديلها |
| **الوراثة** | المجموعة الفرعية **ترث** عضويات المشاريع وصلاحيات المجموعة الأب |
| **الفائدة** | إدارة فعالة للفرق الكبيرة والهياكل التنظيمية المعقدة |
| **التأثير** | أي مستخدم في مجموعة فرعية يحصل تلقائيًا على صلاحيات المجموعة الأب |

**ما يمكن فعله بالمجموعات:**

- ✅ تعيين أدوار مشروع للمجموعة
- ✅ مشاركة حزم عمل مع مجموعة
- ✅ إنشاء هرمية مجموعات (Parent → Child)
- ✅ تعيين مستخدمين متعددين للمجموعة

**ما لا يمكن فعله بالمجموعات:**

- ❌ تعيين أدوار عامة (Global Roles) للمجموعة — الأدوار العامة تُعيّن للمستخدمين الأفراد فقط
- ❌ إضافة مستخدمين مؤقتين (Placeholder Users) للمجموعات

### الآلية 2: المستخدمون المؤقتون (Placeholder Users)

> **المصدر:** [Placeholder Users](https://www.openproject.org/docs/system-admin-guide/users-permissions/placeholder-users/)

| الخاصية | القيمة |
| --------- | -------- |
| **الغرض** | تخطيط الموارد وتعيين المهام دون حساب مستخدم حقيقي |
| **مكان الإنشاء** | Administration → Users and Permissions → Placeholder Users |
| **الإصدار** | ⚡ Enterprise Edition فقط |

**الوصف الرسمي:**

المستخدمون المؤقتون هم كيانات افتراضية تُستخدم في مرحلة التخطيط والقوالب، وهم لا يستهلكون ترخيصًا (license seat).

**خصائص المستخدم المؤقت:**

| الخاصية | القيمة |
| --------- | -------- |
| **يمكن تعيينه لمشاريع** | ✅ نعم — كعضو مباشر |
| **يمكن تعيين حزم عمل له** | ✅ نعم |
| **يمكن إضافته لمجموعات** | ❌ لا |
| **يمكن تعيين أدوار عامة له** | ❌ لا |
| **يستهلك ترخيصًا** | ❌ لا |
| **يمكن تسجيل دخوله** | ❌ لا |
| **يمكن استبداله بمستخدم حقيقي** | ✅ نعم — عند الانتقال من التخطيط للتنفيذ |

**الصلاحية المطلوبة لإدارة المستخدمين المؤقتين:**

- صلاحية عامة: `Manage placeholder user`

### الآلية 3: الوحدات (Modules) — بوابة تفعيل الصلاحيات

> **المصدر:** [Project Settings - Modules](https://www.openproject.org/docs/user-guide/projects/project-settings/modules/)

| الخاصية | القيمة |
| --------- | -------- |
| **الغرض** | التحكم في الميزات المتاحة داخل كل مشروع |
| **مكان الإدارة** | Project Settings → Modules |
| **التأثير** | تعطيل وحدة يُعطل جميع الصلاحيات المرتبطة بها |

**الوصف الرسمي:**

الوحدات تعمل كـ **بوابة (gateway)** للصلاحيات على مستوى المشروع. هذه نقطة حاسمة في فهم نظام الصلاحيات:

```
صلاحية فعّالة = دور المستخدم يتضمن الصلاحية ✅
                + الوحدة المقابلة مُفعّلة في المشروع ✅
```

**مثال:**

| السيناريو | الدور يتضمن الصلاحية | الوحدة مُفعّلة | النتيجة |
| ----------- | ---------------------- | --------------- | --------- |
| تعديل حزم عمل | ✅ | ✅ Work Packages | ✅ مسموح |
| تعديل حزم عمل | ✅ | ❌ Work Packages معطلة | ❌ مرفوض |
| تعديل الويكي | ✅ | ✅ Wiki | ✅ مسموح |
| تعديل الويكي | ✅ | ❌ Wiki معطلة | ❌ مرفوض |

**قائمة الوحدات المتاحة (من الوثائق الرسمية):**

1. Work Packages (حزم العمل)
2. Gantt Charts (مخططات جانت)
3. Agile Boards (لوحات Agile)
4. Backlogs (القوائم المتأخرة)
5. Calendar (التقويم)
6. News (الأخبار)
7. Forums (المنتديات)
8. Wiki (الويكي)
9. Repository (المستودع)
10. Time Tracking (تتبع الوقت)
11. Costs (التكاليف)
12. Budgets (الميزانيات)
13. Meetings (الاجتماعات)
14. Team Planner (مخطط الفريق)
15. File Storages (تخزين الملفات)

### الآلية 4: قوالب المشاريع (Project Templates)

> **المصدر:** [Project Templates](https://www.openproject.org/docs/user-guide/projects/project-templates/)

| الخاصية | القيمة |
|---------|--------|
| **الغرض** | توحيد إعدادات الصلاحيات عبر المشاريع الجديدة |
| **مكان الإدارة** | Projects → Project Templates |

**الدور في نظام الصلاحيات:**

قوالب المشاريع تعمل كآلية **توحيد** (standardization) لإعدادات الصلاحيات:

- يمكن تهيئة القالب مسبقًا بـ:
  - المجموعات والأدوار المطلوبة
  - الوحدات المُفعّلة
  - أنواع حزم العمل المتاحة
  - الإعدادات الافتراضية
- عند إنشاء مشروع جديد من القالب، يتم نسخ كل هذه الإعدادات تلقائيًا

**أهمية خاصة:** بما أن OpenProject **لا يدعم** توريث الصلاحيات من مشروع أب إلى مشروع فرعي، فإن القوالب تُعتبر **البديل العملي** لضمان اتساق الصلاحيات عبر المشاريع.

---

## الجزء الثالث: قواعد معمارية مهمة

### 1. لا يوجد توريث صلاحيات بين المشاريع (No Inheritance)

> **مصادر متعددة تؤكد هذا:**

OpenProject **لا يدعم** توريث أو انتشار (propagation) أدوار الأعضاء والصلاحيات من مشروع أب إلى مشاريعه الفرعية.

| الجانب | الحالة |
| -------- | -------- |
| **عضوية المشروع الأب → الفرعي** | ❌ لا توريث تلقائي |
| **صلاحيات المشروع الأب → الفرعي** | ❌ لا توريث تلقائي |
| **كل مشروع مستقل** | ✅ نعم — يُدار بشكل منفصل |

**الحلول البديلة الرسمية:**

1. **استخدام المجموعات:** تعيين نفس المجموعة لكل من المشروع الأب والفرعي
2. **استخدام القوالب:** إنشاء قالب يتضمن المجموعات والأدوار المطلوبة

### 2. الصلاحيات تراكمية (Additive Permissions)

عندما يحمل المستخدم أكثر من دور (سواء مباشرة أو عبر مجموعات)، الصلاحيات **تتراكم**:

- ✅ الصلاحية النهائية = مجموع صلاحيات جميع الأدوار
- ❌ لا يوجد مفهوم "الرفض الصريح" (Explicit Deny)
- ❌ لا يوجد أولوية لدور على آخر

**مثال:**

```
دور A: عرض حزم العمل ✅ + تعديل حزم العمل ❌
دور B: عرض حزم العمل ✅ + تعديل حزم العمل ✅
────────────────────────────────────────────
النتيجة: عرض حزم العمل ✅ + تعديل حزم العمل ✅ (التراكم)
```

### 3. تعدد الأدوار (Multiple Roles)

يمكن لمستخدم واحد أن يحمل:

- أدوار عامة (Global Roles) متعددة
- أدوار مشروع (Project Roles) مختلفة في مشاريع مختلفة
- **أكثر من دور** في نفس المشروع
- كل هذا بالتوازي مع بعضه

## الجزء الرابع: آلية تقييم الصلاحيات (Permission Evaluation Flow)

> **مُستنتج من الوثائق الرسمية المتعددة:**

عند محاولة مستخدم تنفيذ إجراء معين، يتم تقييم الصلاحية وفق التسلسل التالي:

```
المستخدم يطلب إجراءً
        │
        ▼
┌───────────────────┐
│ هل هو Administrator? │──── نعم ──→ ✅ السماح (دائمًا، بلا فحص إضافي)
└───────────────────┘
        │ لا
        ▼
┌───────────────────────┐
│ هل لديه دور عام يشمل  │──── نعم ──→ ✅ السماح
│ هذا الإجراء؟           │           (للإجراءات العامة فقط)
└───────────────────────┘
        │ لا
        ▼
┌────────────────────────┐
│ هل هو عضو في المشروع؟  │
│ (مباشرة أو عبر مجموعة) │──── لا ──→ فحص Non-member/Anonymous
└────────────────────────┘
        │ نعم
        ▼
┌─────────────────────────┐
│ هل أدواره (المُجمّعة)   │──── لا ──→ ❌ الرفض
│ تتضمن الصلاحية؟         │
└─────────────────────────┘
        │ نعم
        ▼
┌──────────────────────────┐
│ هل الوحدة المطلوبة       │──── لا ──→ ❌ الرفض
│ مُفعّلة في المشروع؟      │          (الصلاحية معطلة ضمنيًا)
└──────────────────────────┘
        │ نعم
        ▼
     ✅ السماح
```

## الجزء الخامس: جدول المقارنة الشامل

### مقارنة المستويات التنظيمية الأربعة

| المعيار | النظام (System) | العام (Global) | المشروع (Project) | حزمة العمل (Work Package) |
| --------- | ---------------- | ---------------- | ------------------- | -------------------------- |
| **نوع الدور** | Administrator | Global Role | Project Role | Sharing Level |
| **النطاق** | المثيل بالكامل | المثيل بالكامل | مشروع واحد | حزمة عمل واحدة |
| **قابل للتخصيص** | ❌ | ✅ | ✅ | ✅ (3 مستويات) |
| **يتطلب عضوية مشروع** | ❌ | ❌ | ✅ | ❌ |
| **يتأثر بالوحدات (Modules)** | ❌ | ❌ | ✅ | ✅ |
| **عدد الأدوار** | 1 (ثابت) | متعدد (مخصص) | متعدد (مخصص + مدمج) | 3 (View/Comment/Edit) |
| **من يديره** | مدير النظام | مدير النظام | مدير المشروع | عضو المشروع المُخوّل |
| **التعيين عبر مجموعات** | ❌ (فردي) | ❌ (فردي) | ✅ | ✅ |
| **الإصدار** | Community + Enterprise | Community + Enterprise | Community + Enterprise | Enterprise فقط |

### مقارنة الآليات المساعدة

| الآلية | النوع | الغرض | التأثير على الصلاحيات | الإصدار |
| -------- | ------- | ------- | ---------------------- | --------- |
| **Groups** | تجميع مستخدمين | تسهيل تعيين الأدوار جماعيًا | غير مباشر — وراثة أدوار المجموعة | Community + Enterprise |
| **Placeholder Users** | كيان افتراضي | تخطيط الموارد | محدود — عضوية مشروع فقط | Enterprise فقط |
| **Modules** | بوابة تفعيل | تفعيل/تعطيل ميزات | مباشر — تعطيل الوحدة يُلغي الصلاحيات | Community + Enterprise |
| **Project Templates** | قالب إعدادات | توحيد الصلاحيات | غير مباشر — نسخ الإعدادات عند الإنشاء | Community + Enterprise |

## الجزء السابع: الفروقات المفاهيمية الدقيقة

| المفهوم | التعريف | مثال في OpenProject |
| --------- | --------- | --------------------- |
| **المستوى التنظيمي** (Organizational Level) | طبقة في التسلسل الهرمي تُحدد **أين** تُطبق الصلاحيات | System, Global, Project, Work Package |
| **النطاق** (Scope) | مدى تأثير دور أو صلاحية معينة | "هذا الدور يعمل على مستوى المشروع فقط" |
| **السياق** (Context) | الظرف أو البيئة التي يتم فيها فحص الصلاحية | "هل المستخدم يعمل داخل مشروع X أم في واجهة الإدارة؟" |
| **الآلية المساعدة** (Helper Mechanism) | أداة تنظيمية تُسهل تطبيق الصلاحيات | Groups, Modules, Templates |
